# ADR 0022: UUIDv7 Is the Primary Key of Every Entity; the Only Sequence Is the Ticket Number per Project

## Status

Accepted. Date: 2026-09-30. Decided by the owner as the answer to the catalog question
"identifiers?": database-generated UUIDv7 for every entity, over bigint sequences with an
external UUID and over UUIDv4.

**Partly built.** `tenants.id uuid PRIMARY KEY DEFAULT uuidv7()` in migration
[`000001_tenants`](../../backend/internal/store/migrations/000001_tenants.up.sql); no other
table exists.

## Context

[ADR 0001](0001-two-containers-a-go-backend-and-an-nginx-frontend-installed-by-one-helm-chart.md)
D5 made PostgreSQL 18 the minimum so that `uuidv7()` is available, and
[ADR 0007](0007-a-ticket-key-is-globally-unique-tenant-slash-project-dash-number.md) D5 kept
UUIDv7 as the ticket's primary key under its human key. What remained was to extend the rule
to every table and to close the door on human keys as foreign keys. UUIDv7 is time-ordered,
which the API's cursor pagination and the activity list's ordering can use directly;
UUIDv4 would need a `(created_at, id)` cursor and fragments indexes; bigint sequences leak
counts and need a second identifier at the API edge.

## Decision

**D1 — Every entity's primary key is a `uuid` generated by the database with
`DEFAULT uuidv7()`.** The application never generates an id and never supplies one on
insert; the row's id is what the insert returns.

**D2 — The only sequence is the ticket number per project** (ADR 0007 D4), implemented as a
counter row per project updated in the ticket's insert transaction, never a PostgreSQL
sequence — a sequence cannot be per project and must never reuse a number after a rollback.

**D3 — Foreign keys reference UUIDs, never human keys.** A ticket's parent, a link's ends, a
comment's ticket, an attachment's owner: all by UUID. The human key of ADR 0007 is a unique
index and an address, not a relation.

**D4 — In the API, an id is the UUID string; a ticket is additionally addressable by its
canonical key.** No URL is built from a UUID where a key or a slug exists (tenants, projects,
tickets); entities without a human name (comments, attachments, questions, time entries,
notifications) are addressed by UUID under their ticket's path.

**D5 — Ordering by id is ordering by creation time.** Cursor pagination (the API record) and
"newest first" lists use the id; no separate `created_at` index is needed for that purpose,
though the column exists for display.

## Consequences

- One id type across the schema, the generated data layer and the API.
- 16 bytes per key and per index entry instead of 8 — irrelevant at the expected sizes.
- An import or a later merge of two installations cannot collide on ids; the ticket number
  is the only thing an import has to place (ADR 0007 D6).
- D2's counter row is a serialisation point per project; two tickets filed in the same
  project at the same instant queue on it for a millisecond, which is the price of a number
  that never repeats.

## Alternatives Considered

- **Bigint sequences as primary keys, UUID only outward.** Smaller indexes; two ids per row,
  a mapping at every API boundary, and sequential ids that reveal counts for comments,
  tokens and attachments. Lost.
- **UUIDv4.** Random, so no time order and fragmented indexes; nothing gained over v7 on
  PostgreSQL 18. Lost.
- **A PostgreSQL sequence per project for the ticket number.** Creating a sequence per
  project is possible but leaves gaps on rollback and is awkward to import into. Lost to D2.

## Residual risks

- D5 leans on UUIDv7's millisecond ordering; two rows created within the same millisecond
  order by the random part. Lists that must be strictly stable within a millisecond do not
  exist here.
